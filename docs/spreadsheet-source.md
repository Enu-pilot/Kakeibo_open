# スプレッドシートを軸にした家計簿の設計検討

> **このメモの後の経緯:** データの置き場は PostgreSQL から Google スプレッドシートに移った
> （[`requirements.md`](requirements.md) §10）。このメモの「DB」「DB 版」は、いまは
> **アプリ専用のスプレッドシート**（アプリが読み書きする側）を指す。「シート」「シート版」は
> GAS 時代の請求シート（アプリは読むだけ）のまま。接続は同じサービスアカウントにまとめ、
> 請求シートは読み取り専用のスコープで開く（`requirements.md` 決定 28）。

「家計簿アプリを、スプレッドシートのデータの可視化として作れないか」という検討のメモ。
まだ決定ではなく、選択肢と分岐点を並べたもの。確定した仕様は
[`requirements.md`](requirements.md) のままで、ここが本文を上書きするわけではない。

---

## 0. 何を決める話なのか

現在のアプリは **DB が正（source of truth）** で、CSV はそこへの入力経路にすぎない。
「スプレッドシートの可視化」にするというのは、つまり
**正をどこに置くか** を動かす話になる。ここさえ決まれば、あとの設計は自動的に決まる。

| 正の置き場所 | 入力する場所 | アプリの役割 |
|---|---|---|
| スプレッドシート | Sheets | 読んで描くだけ（案A） |
| DB | Sheets → 同期 | 取り込み・分類・編集・可視化（案B） |
| DB | アプリ（現状） | 現状どおり、シートは入口のひとつ（案C） |

**決定：既存のアプリは置き換えず、シート版を並行して持つ。**
したがって上の表は「既存アプリをどうするか」ではなく、
**並行して足すほうがどの経路でデータを読むか**の選択になる。
既存の DB 版は、どの案を選んでも今までどおり動き続ける。
並行構成そのものの設計は §8 にまとめた。

## 1. 現行コードの接合点

幸い、今の実装はデータ源を差し替えやすい形になっている。実測した接合点は次の 2 か所だけ。

### 1-1. 集計側 — `src/lib/aggregate.ts`

DB を触っているのは実質 2 行しかない。

| 箇所 | 内容 |
|---|---|
| `src/lib/aggregate.ts:55` | 内訳（split）の取得 |
| `src/lib/aggregate.ts:201` | 大項目の一覧（まとめ表の段組み） |

`getKindTotals` / `getMonthlyTrend` / `getCategoryBreakdown` / `getSummaryMatrix` と、
その先のグラフ・まとめ表は、この 2 か所が返す `SplitRow[]` の形さえ作れれば
**データ源が何でもそのまま動く**。純残高の計算（`netBalance`）も純粋関数。

### 1-2. 取込側 — `src/lib/csv.ts`

`ParsedTable = { headers: string[]; rows: Record<string, string>[] }`（`src/lib/csv.ts:39`）が
取込パイプラインの入口で、その先は全部この型にしか依存していない。

```
ファイル ──decodeCsv──> テキスト ──parseCsv──> ParsedTable ──guessMapping──> ColumnMapping
                                                      └──mapRow──> MappedRow[] ──> 分類 ──> commit
```

`ParsedTable` を作れる経路を増やせば、**列マッピング UI・プリセット・使用先の中項目化・
個人支出/生活費の 2 列分割・重複判定・バッチ取り消しがそのまま効く**。
実際に `ParsedTable` を組み立てているのは `src/components/import/import-wizard.tsx:91` の
1 行だけで、以降（`:108` の推測、`:115` の行変換）は共通。

## 3. 案A — スプレッドシートを唯一のデータ源にする

アプリを読み取り専用のビューアにする案。GAS の資産と、スマホの Sheets アプリで
追記できる手軽さをそのまま残せるのが利点。

### 3-1. 必要になるもの

1. **カテゴリ定義シート**が新たに要る。
   今は「中項目 → 大項目 → 種別（kind）」の対応が DB にあり、これが純残高計算の根拠になっている
   （`requirements.md` §3 決定 1）。シートを正にするなら、この対応表もシート上に置くしかない。
   `中項目名 / 大項目名 / 種別` の 3 列のシートが最低限必要。
2. **範囲指定**。GAS の `請求YYYY` はカードごとの 4 列組が**横に並ぶ**構造（`requirements.md` §1）。
   `ParsedTable` は単一ヘッダー行を前提にしているので、シートまるごとではなく
   A1 記法の範囲（`請求2026!A1:D500` など）でブロックを切り出して読む必要がある。
3. **キャッシュ**。ダッシュボードは直近 12 か月ぶんを毎回スキャンする。
   ページ表示のたびに Sheets API を叩くと遅く、クォータも食うので、
   一定時間のキャッシュか手動の「再読み込み」ボタンが要る。

### 3-2. 失うもの

`dedupeHash` による重複スキップ、手修正からのルール学習（`requirements.md` §6 決定 10）、
明細のインライン編集、取込バッチの取り消し。いずれも「シート側で手で直す」に戻る。
書き込みまで実装すれば一部は取り戻せるが、シートを人間も同時に触る前提だと
競合とバリデーションの面倒が実装量を押し上げる。

### 3-3. 実装の形

`loadSplits` を差し替えるのではなく、`SplitRow[]` を返す**プロバイダを切る**形にすると、
DB 版とシート版を両方残したまま試せる。集計関数より下だけが入れ替わる。

## 4. 案B — シートを入力に、DB を集計層にする（推奨）

取込ウィザードに「Google スプレッドシートから読む」経路を足す案。
体感としては「シートに書いてアプリで見る」になり、機能は何ひとつ失わない。

### 4-1. 実装の形

- サーバー側に読み取り用のルートを 1 本足し、`ParsedTable` を返す。
  認証情報はサーバーにしか置けないので、クライアント直読みにはできない。
- ウィザードは `ParsedTable` の作り方が「ファイル」か「シート」かの分岐になるだけ。
  プレビュー・分類・確定（`src/app/api/import/commit/route.ts`）は一切変わらない。

### 4-2. プリセットの拡張

`ImportPreset.mapping` は `Json` 列なので、**マイグレーションなしで**
`spreadsheetId` / `range` を同居させられる（型 `ColumnMapping` の拡張だけで済む）。
`skipRows` も既にあるので、ヘッダー行の前の説明行はそのまま吸収できる。
カード会社ごとにプリセットを作る今の運用が、そのままシートのブロックごとのプリセットになる。

### 4-3. 再同期の扱い（要判断）

`dedupeHash`（日付 + 利用先 + 金額 + 決済手段）があるので、**同じ行を二重に取り込むことはない**。
何度同期しても増えるのは新しい行だけ。

ただし**シート側で後から直した行はアプリに反映されない**。金額を直しても
ハッシュが変わるので「別の明細」として増えてしまう。反映したいなら
`Transaction` に「どのシートの何行目か」を表す行キー列を足し、
ハッシュではなくそれで突き合わせる必要がある（スキーマ変更あり）。

→ **シートは追記のみで、修正はアプリ側でやる**と決めるなら、行キーは不要で実装が軽い。

### 4-4. 認証

- サービスアカウントを作り、対象のスプレッドシートをそのアドレスに**閲覧者**で共有する
- スコープは `spreadsheets.readonly` に限定する
- 環境変数は 3 つ（サービスアカウントのメール、秘密鍵、対象スプレッドシート ID）。
  秘密鍵は改行を含むので、格納時のエスケープに注意が必要
- `googleapis` パッケージは重いので入れない。**署名用の `jose` は既に依存にあり**、
  JWT を自前で署名してアクセストークンを取り、`values` エンドポイントを叩けば
  依存を増やさずに済む
- シートを「リンクを知っている全員」にして公開 CSV URL を読む手もあるが、
  家計データなので採らない

## 5. 案C — 貼り付け / ファイル取込を足すだけ

「スプレッドシートの範囲を選んでコピー → アプリに貼り付け」で取り込む経路。
クリップボードはタブ区切りのテキストなので、区切り文字を変えるだけで
既存の `parseCsv` がそのまま使える。**依存追加ゼロ・認証ゼロ**で、
案 B の体験のかなりの部分が手に入る。

`.xlsx` ファイルそのものを受けたい場合は別途パーサの依存が要るが、
Sheets が手元にあるなら貼り付けのほうが軽い。

## 6. 未決事項

実シートを見ないと確定できないもの、運用の意向で決まるものを分けて挙げる。

1. **シート版の読み取りを、まず貼り付けで始めるか、最初から Sheets 直読みにするか。**
   貼り付けなら今日から動かせる。直読みはサービスアカウントの用意と、
   対象シートの ID・範囲の確定が先に要る（§4-4）。
2. **シートで直した内容をアプリに反映する必要があるか。**
   必要なら案 B に行キーの追加（スキーマ変更）が要る（§4-3）。
3. **カテゴリ定義をどこが持つか。** 並行構成では DB から借りるのが軽い（§8-3）。
   案 A まで進める場合はカテゴリ定義シートが必須（§3-1）。
4. ~~**`請求YYYY` の実際のブロック配置。**~~ → 確認済み。§9 にまとめた。
6. ~~**払い戻しを DB でどう持つか。**~~ → 決定。DB でもマイナスで持ち、その中項目から差し引く
   （要件定義 §4 決定 5 の改訂）。符号の規則は取込・シート読み取り・手入力で共通。
7. ~~**給料の扱い。**~~ → 決定。**アプリは口座ベースで集計する。**
   まとめシートの「収入」（総支給の内訳）は税金の計算用に手元で付けているもので、お金の出入りではない。
   収入として数えるのは口座への振込である「給料」だけにする。
   まとめシートで給料がマイナスなのは、口座ブロックが「出金がプラス」の向きで書かれているため
   （シート版は入金として読み、収入のプラスに直す）。
   項目を一括作成するときは「収入内訳」の行を外す（確認の表で除外できる）。
5. **既存の GAS（請求 → 支出 → まとめ）を残すか、止めるか。**
   残すなら、アプリと GAS が同じシートを触ることになるので、書き込みは避けたほうがよい。

## 7. 進め方の案

並行構成なので、既存の動作を壊さない順に積める。

1. **計算と読み込みを分離する（§8-2）** — 既存の画面・挙動は一切変わらない。
   ここを先にやると、以降どの案を選んでも土台が共通になる
2. **貼り付け経路でシート版の画面を出す（案C）** — 認証なしで、
   シートの範囲をコピーして貼れば同じグラフが描ける。
   ここで実シートの列構成がアプリの想定と合うかを確かめられる
3. **突合画面で数字を確かめる（§8-4）** — DB 版とシート版で同じ月を集計し、差分を見る。
   シート版の読み取りが正しいかの検証になる
4. **合っていれば Sheets 直読みに進む（案B/A）** — 認証を入れ、
   2 で固めたマッピングをプリセットに持たせて同期ボタン 1 つにする

1〜3 は既存機能に触れないので、途中で止めても損にならない。

## 8. 並行構成の設計

既存のアプリを残したままシート版を並べることで、
今の運用を止めずに試せ、数字が合っているかを突合でき（§8-4）、
気に入らなければシート版だけ捨てられる。

### 8-1. 共有するもの / 分けるもの

| 層 | 扱い |
|---|---|
| グラフ部品（`src/components/charts/*`）・まとめ表・系列色 | **共有**。props しか見ていないので両方でそのまま使える |
| 集計の計算 | **共有**。ただし今は読み込みと混ざっているので分離が要る（§8-2） |
| データの読み込み | **分ける**。DB 版 / シート版の 2 実装 |
| 画面 | **分ける**。シート版は別セクションに新設し、既存画面は触らない |
| 取込・設定・明細編集 | **DB 版のみ**。シート版は読み取り専用に割り切る |

### 8-2. 必要な分離（既存コードへの唯一の変更）

今の `aggregate.ts` は 4 つの集計関数がそれぞれ内部で `loadSplits`（`src/lib/aggregate.ts:55`）を
呼んでいる。これを「読み込み」と「計算」に割る。

```
src/lib/aggregate.ts       export の形は維持（＝画面は無変更）。中身は下へ委譲するだけになる
src/lib/aggregate-core.ts  純粋な計算。SplitRow[] を受けて集計結果を返す
src/lib/source/types.ts    SplitRow・大項目の型と、データ源のインターフェース
src/lib/source/sheet.ts    シートから SplitRow[] を組む（新規）
```

要点は **`aggregate.ts` の export を変えないこと**。
`getKindTotals(from, to)` などの呼び出し側（`src/app/(app)/page.tsx:46` ほか）を
書き換えずに済み、既存の画面は今までどおり DB を見続ける。
この分離は単体で意味が通るので、シート版を作らなくても無駄にならない。

### 8-3. カテゴリ定義をどちらが持つか（要判断）

§3-1 と同じ問題が並行構成でも出る。シートの行には中項目名しかないが、
集計には「その中項目がどの大項目・どの種別か」が要る。並行なら選べる。

- **DB のカテゴリ定義を借りる（推奨）** — シートは日付・利用先・金額・中項目名だけを持ち、
  大項目・種別・色は既存の DB から引く。定義を二重管理せずに済み、
  設定画面もそのまま効く。シート版が完全には独立しなくなるのが難点
- **カテゴリ定義シートを作る** — 完全に独立するが、DB 側と定義がずれたとき、
  突合して数字が合わない理由が「データの差」なのか「定義の差」なのか分からなくなる

### 8-4. 突合画面

並行させる利点を活かすなら、**同じ月を DB とシートの両方で集計して差分を出す**画面を作る。
移行するかどうかの判断材料になり、シート版の読み取りが正しいかの検証にもなる。
まとめ表の構造（`getSummaryMatrix`）をそのまま 2 本並べて引き算すれば済むので、
§8-2 の分離さえ終わっていれば実装は軽い。

## 9. 請求シートの実構造（確認済み）

実物のヘッダー 2 行を読んで確かめた結果（ブロック名は公開用に一般名へ置き換えている）。**11 ブロックが横に並ぶ。**

| ブロック | 列範囲 | 列数 | 日時 | 内容 | 金額 | 使用先 |
|---|---|---|---|---|---|---|
| カードA | 0–12 | 13 | 2 | 3 | 8 | 12 |
| PayPay | 14–22 | 9 | 14 | 20 | 21 | 22 |
| カードB | 24–36 | 13 | 25 | 26 | 30 | 36 |
| カードC | 38–50 | 13 | 40 | 41 | 46 | 50 |
| カードD | 52–61 | 10 | 52 | 53 | 60 | 61 |
| カードE | 63–70 | 8 | 63 | 64 | 65 | 70 |
| 通販サイト | 72–79 | 8 | 72 | 73 | 74 | 79 |
| 銀行口座 | 81–87 | 7 | 81 | 84 | 86 | 87 |
| 現金 | 89–92 | 4 | 89 | 90 | 91 | 92 |
| 電子マネーA | 94–97 | 4 | 94 | 95 | 96 | 97 |
| 交通系IC | 99–105 | 7 | 99 | 101 | 104 | 105 |

### 読み取りの手がかりになった規則

- **どのブロックにも `日時` / `内容` / `金額` / `使用先` が必ずある。**
  列数は 4〜13 とばらばらで、間に挟まる列（支払区分・残高・訂正サインなど）も
  カードごとに違うが、この 4 列だけは共通。要件定義 §1 の「4 列組」がこれにあたる。
  **この 4 列を契約とみなし、他の列は読み飛ばす**設計にした。
- **ブロックの切れ目は `使用先` 列。** その右に空列を 1 つ挟んで次のブロックが始まる。
  カードごとのプリセットを人が用意しなくても、切れ目は自動で判定できる。

### 実装で踏まえた落とし穴

| 落とし穴 | 対応 |
|---|---|
| 一部のカードは `ご利用金額(￥)` と `金額` の**両方**を持つ | CSV 取込の推測に任せると `ご利用金額(￥)` が先に当たる。4 列は**完全一致を最優先**して `金額` を選ぶ |
| 銀行口座だけ `お引出し` / `お預入れ` / `残高` を持つ | `お預入れ` に値があれば入金として扱う。入金なのに収入以外の大項目に入る行は警告に出す |
| 交通系IC などヘッダーが**空**の列がある | 空ヘッダーは位置から `列N` に振り直す。そのままだとキーが衝突して別の列を読む |
| 同じヘッダー名がブロック内に複数ある | 2 つ目以降に連番を付けて区別する |
| 1 行目のブロック名は、貼り付けると列がずれることがある | 位置の完全一致ではなく、**未使用の名前のうちブロック先頭に最も近いもの**を採る。名前の数とブロック数が食い違う場合は画面に警告を出す |

### 金額の符号（実データで確認）

シートの金額には**符号がある**。まとめシートでは支出側の項目にもマイナスが普通に現れる
（払い戻し・精算。年をまたいで精算され、イベントの期間合計がマイナスになるものもある）。
CSV 取込と同じく絶対値で読むと、払い戻しが支出に**足し込まれて**しまうため、シート版では
種別ごとの本来の向きと逆の行を**マイナスとして持ち、その中項目から差し引く**。

| 種別 | プラス | マイナス |
|---|---|---|
| 収入系 | 入金 | 出金 |
| それ以外 | 出金 | 入金（払い戻し・精算） |

まとめシートの実際の数字（ある旅行の 2025/01 −283,499、2025/02 +274,666、期間合計 −8,833）と
同じ値になることを確かめた。

> DB 側も同じ規則に改めた（要件定義 §4 決定 5 の改訂）。払い戻しはどちらでも差し引かれるので、
> 突合で払い戻しが原因の差分は出ない。

### 中項目の決め方

シートの行には中項目名（`使用先`）しかないため、大項目と種別は DB のカテゴリ定義から引く（§8-3 の推奨どおり）。
取り込んだ場合と数字がずれないよう、既存の取込と同じ順序で決める。

1. `使用先` と同名の中項目があればそれ
   - 名前に「投資」が含まれるときは投資の大項目を優先（GAS からの引き継ぎ。`/api/categories/ensure` と同じ扱い）
   - 同名が複数の大項目にある（`支出/食費` と `生活費/食費` など）ときは、
     内容から自動分類ルールで決まればそれ、決まらなければ大項目の並び順が先のもの
2. 決まらなければ内容に対する自動分類ルール
3. それでも決まらなければ `未分類`

どの経路で決まったかは件数を画面に出すので、推測がどれだけ混ざっているかが分かる。

### 突合（§8-4）

シート画面で読み込むと、シートに出てくる月の範囲だけ DB を読み、同じ集計にかけて引き算する。
差分は **シート − DB**。プラスはシートにだけある金額（DB に取り込まれていない）、
マイナスは DB にだけある金額。シート版は DB のカテゴリ定義を借りているので、
中項目の id が両者で一致し、**中項目の単位まで**差分を出せる。

- 金額は Decimal なので、浮動小数の誤差で 0 にならない差分が出ないよう銭単位で丸めて比べる
- DB に明細が 1 件も無い月は「まだ取り込んでいない」ことが多いので、別に挙げる

### Sheets 直読み（§4-4）

§4-4 の設計どおり、`googleapis` は入れずに既存の `jose` で JWT を署名している。

- スコープは `spreadsheets.readonly` のみ。アプリからシートを書き換えることは構造上できない
- 値は `FORMATTED_VALUE`（画面に見えている文字列）で取る。`2026/01/15` `3,200` のまま返るので、
  CSV 取込と同じ日付・金額の解釈をそのまま通せる
- API は**末尾の空セルを落とす**。1 行目のブロック名の行は短くなるが、§9 の
  「最近傍で割り当てる」方式がそのまま吸収する（貼り付けで列がずれる問題と同じ）
- 取得したトークンは 1 時間使えるので、使い回して毎回の往復を省く

設定手順は README の「スプレッドシートを直接読む」。
