# 家計簿 Web アプリ 要件定義書（確定版）

ドラフトのうち曖昧だった点を確定させ、実装済みの仕様として書き直したもの。
「決定」欄が、ドラフトから変更・具体化した箇所。

---

## 0. 確定した前提

| 項目 | 決定 | 理由 |
|---|---|---|
| 利用形態 | 自分専用。PC か Codespace の中だけで動かし、インターネットに公開しない | URL を持って外部から到達できる状態を避けたい。多少の手間より堅牢さを取る（§10） |
| 認証 | 単一アカウントのパスワード認証（`APP_PASSWORD`） | 利用者が 1 人なのでユーザー管理は不要 |
| DB | Google スプレッドシート（Sheets API） | Codespace を作り直してもデータが残り、版履歴があり、スプレッドシートで直接見て直せる（§10） |
| レシート OCR | 第 2 フェーズ送り | まず CSV と手入力で運用を回す。`明細` タブに `レシートURL` 列は用意済み |
| CSV の取り込み方 | 汎用の列マッピング UI ＋ プリセット保存 | カード会社ごとの専用パーサを作らずに全社対応する |
| 大項目 | ユーザーが自由に追加・改名・削除できる | 運用しながら育てられるようにする |

## 1. これまでの GAS との対応

運用していた Google Apps Script の考え方をそのまま持ち込んでいる。対応は次のとおり。

| GAS | アプリ | 補足 |
|---|---|---|
| `請求YYYY` シート（カード明細の生データ） | CSV 取込 | カードごとの 4 列組（日時 / 内容 / 金額 / 使用先）を列マッピングで受ける |
| `使用先` 列 | 中項目 | 取込時に「使用先を中項目にする」と、無い中項目は自動で作られる |
| `支出YYYY` シート（使用先ごとの集計） | 明細＋まとめ | 使用先が中項目になるため、集計は「まとめ」がそのまま担う |
| `自己負担額`（col+4）/ `家計負担`（col+6） | **明細の内訳（split）** | 1 件の明細を 2 つの大項目に分ける。§2 参照 |
| `食費判定`（col+5） | 取り込まない | GAS の集計も読んでいない（col+1 / col+4 / col+6 のみ参照）シート上の作業用フラグ。食費かどうかは中項目と分類ルールで表す |
| 大項目 `給料` | 大項目「給料」（種別 = 収入） | まとめで収入と別ブロックだったため独立させた |
| 大項目 `チャージ関連` | 大項目「チャージ関連」（種別 = 帳尻合わせ） | 帳尻合わせと同じ種別なので合計は合流する |
| `家族関係` → `生活費` に読み替え | 生活費の中項目「家族関係」 | 大項目を潰さず、生活費配下の中項目として持つ |
| 中項目に「投資」が含まれたら大項目を投資に | 取込時に同じ判定を実施 | `使用先` が「投資積立」なら投資大項目へ入る |
| `まとめ` シートのブロック順 | 大項目の並び順 | 収入 → 給料 → 支出 → 投資 → 帳尻合わせ → チャージ関連 → 生活費 |
| `★XX合計` / `--- 小計 ---` | まとめ表の種別合計 / 大項目小計 | |
| `期間合計` 列 | まとめ表の「合計」列 | |

## 2. 明細の内訳（個人支出と生活費の分割）

**決定 0：1 件の明細は複数の大項目に分けられる。**

GAS では 1 行の買い物を `個人支出` 列と `生活費` 列に手で振り分け、
集計時に別々の大項目へ計上していた。これが「生活費と個人支出を分ける」運用の中身なので、
アプリでも 1 明細 = 1 カテゴリにはせず、**内訳（TransactionSplit）** を持たせている。

```
明細: ＪＴＢ 新幹線チケット  32,000 円
  ├ 内訳1  支出   / 帰省   12,000
  └ 内訳2  生活費 / 帰省   20,000
```

- 分けない明細も内訳を 1 件持つ（例外を作らないため）
- 内訳の合計は必ず明細の総額と一致する（金額は内訳から決まる）
- 集計・グラフ・まとめ表はすべて内訳を単位に数える
- 明細一覧をカテゴリで絞ったときの「絞り込み合計」は、
  条件に合う**内訳ぶんだけ**を足す。総額を足すと分割した明細が二重に見えるため
- 分割した明細は自動分類を学習しない（どちらの内訳を覚えるべきか決まらないため）

CSV 取込では、`個人支出` 列と `生活費` 列を指定すると自動で 2 つの内訳になる。
生活費ぶんは「同じ使用先の中項目を生活費の大項目にも作って」割り当てる。
GAS が同じ `title` を別 `major` に計上していたのと同じ形。

## 3. カテゴリ体系

ドラフトでは「大項目」が固定 5 分類として書かれていたが、自由に追加できる方針に変更した。
ただし大項目を完全な自由文字列にすると集計式が成立しないため、**2 階層 + 種別** の構造にした。
これとは別の軸として、内訳ごとに**費目**を付けられる（§3-2）。

```
種別 (CategoryKind, 固定5種)         ← 計算ルールはここで決まる
   └ 大項目 (MajorCategory, 追加自由)  ← 名前・色・並び順は自由
        └ 中項目 (Category, 追加自由)   ← 取引が必ず1つ持つ

費目 (CostType, 追加自由)             ← ツリーとは別の軸。内訳に 0〜1 個
```

> 呼び方の変更: 当初は「種別」と呼び、種別名を「収入 / 支出」としていたが、
> まとめシートの運用に合わせて **「種別」** と呼び、**個人収入 / 個人支出** / 投資 / 生活費 / 帳尻合わせ とした。
> 中身（計算の規則）は変えていない。

### 種別（システム固定・増減しない）

| 種別 | 画面での名前 | 純残高への効き方 |
|---|---|---|
| `INCOME` | 個人収入 | ＋ |
| `EXPENSE` | 個人支出 | − |
| `LIVING` | 生活費 | − |
| `INVESTMENT` | 投資 | − |
| `ADJUSTMENT` | 帳尻合わせ | 効かない（除外） |

**決定 1：大項目は自由に追加できるが、必ず種別のどれかに属する。**
例えば「事業経費」という大項目を足す場合、種別は `EXPENSE` を選ぶ。
これにより、大項目が増えても純残高の計算式は壊れない。

**決定 2：純残高 = 収入 − 支出 − 生活費 − 投資。**
ドラフトには「純残高（収入 − 支出 − 投資）」とあったが、生活費は実際に出ていくお金なので
差し引かないと残高を過大評価する。よって生活費も減算する。

**決定 3：帳尻合わせ（チャージ・振替）は全ての集計から除外する。**
電子マネーチャージは資産が口座間を移動するだけで純資産は変わらない。
集計に入れると、チャージと、そのチャージで払った買い物とで二重計上になる。
ダッシュボードでは金額だけ別途表示し、まとめ表では独立した段として表示する。

**決定 4：初期データの大項目は削除できない（名前・色・種別の変更は可）。**
過去の集計を壊さないための制約。ユーザーが追加した大項目は削除できる。

### 初期データ（サンプル構成）

初期データは、スプレッドシートの「まとめ」の形（種別 → 大項目 → 中項目）に沿った**公開用のサンプル**（`src/lib/db/seed-data.ts`）。
実際の項目名・人の名前・勤務先などは含めていない。名前・並びは画面から自由に変えられる。

| 種別 | 大項目 | 中項目 |
|---|---|---|
| 個人収入 | 給料 | 本業 / アルバイト / 副業 |
| 個人収入 | 旅費補助 | 旅費補助 |
| 個人収入 | 交通費支給（インターン） | 支出側「インターン」と同じ名前 |
| 個人収入 | 家族 | 家族立替 / 帰省費用 / 生活費補助 / 家賃 |
| 個人支出 | インターン / バイト / 旅行 / 日常 / 遊び / パートナー | イベント名・用途（夏の旅行・ガジェット など） |
| 投資 | 投資 | 証券口座 / 投資 |
| 帳尻合わせ | チャージ関連 / 帳尻合わせ | 交通系ICチャージ / 電子マネーチャージ / 入出金が重なるもの |
| 生活費 | 生活費 | 家賃・光熱費 / 通信費 / 食費 / 日用品 / Amazon建て替え / 生活費 |

個人収入の「交通費支給（インターン）」が支出側と**同じ名前の中項目**を持つのは意図どおり。
入金は同じ名前の個人収入の中項目に入るので（§4-1）、インターンの交通費精算が
そのイベントの収入として、支出と並んで見える。

決済手段も、請求シートのブロック名と同じ名前（サンプルではメインカード・PayPay・銀行口座・現金 …）を初期データにしている。
名前が一致すると、シートを読むときに種類（入金の扱い）が登録どおりに決まる。

### 3-2. 費目（ツリーとは別の軸）

**決定 15：費目は大項目 > 中項目の下にもう 1 段足すのではなく、内訳に付ける別の軸として持つ。**

「旅行かつ食費」「マラソンかつ交通費」のように、中項目（イベント）と費目の掛け合わせで集計したい。
ツリーの下に足すと、同じ「交通費」がイベントの数だけ複製される（`docs/category-depth.md`）。
そこで `CostType` を独立したマスタにし、`TransactionSplit.costTypeId`（任意）で 1 つだけ付ける。

- 1 つの内訳に費目は 1 つ。複数にすると費目別の合計が二重になる。分けたいときは内訳を割る
- 付けていない内訳は「未設定」として数える。既存のデータに遡って付けなくても集計は通る
- 付け方: 明細の内訳エディタ / 取込プレビュー / 取込の「費目」列 / シートのブロックの「費目」列 /
  自動分類ルール（店名 → 費目。中項目だけ・費目だけ・両方のルールが持てる）
- 初期データ: 食費 / 食費（遊び）/ 交通費 / 宿泊費 / 衣服 / 日用品 / 趣味（設定で増減・並べ替え可）

## 4. 金額の持ち方

**決定 5（改訂）：金額は「その種別にとって本来の向きならプラス、逆ならマイナス」で保存する。**
増減の向きそのものは大項目の種別が決め、符号は**その向きに対して順か逆か**だけを表す。

| 種別 | プラス | マイナス |
|---|---|---|
| 収入系 | 入金 | 出金（取り消し・返納） |
| それ以外 | 出金 | 入金（払い戻し・精算） |

明細の総額は内訳の合計として決まるため、総額だけを直接書き換えることはできない。
0 円の内訳と、合計が 0 円になる明細は登録できない。

改訂の理由: 当初は「常に正の絶対値」としていたが、実際のまとめシートでは支出側の項目に
払い戻し・精算のマイナスが普通に現れ、年をまたいでイベントの合計がマイナスになるものもあった。
正の値しか持てないと、払い戻しをその中項目から差し引けず、支出に足し込まれてしまう。

「支出 −3,000 円」と「収入 3,000 円」が混在して向きの判定が必要になる、という当初の懸念は、
符号を**種別に対する相対的な向き**にすることで避けている。集計は単純な足し算のままで済み、
規則は `src/lib/category-kind.ts` の `signFor` 1 か所にある（取込・シート読み取り・手入力が共通で使う）。

あわせて、重複判定のハッシュに符号が入るようになった。以前は同じ日・同じ店・同じ額の
「購入」と「返金」が同じハッシュになり、返金が重複として取り込まれずに落ちていた。

スプレッドシートには数値セルとして保存し、読み込み時に小数 2 桁に丸める。日本円は整数だが、外貨・ポイント換算を後から入れられるよう小数 2 桁を扱える形にしている。内訳の合計は銭単位の整数で足し、丸め違いで総額と合わなくなるのを防ぐ。

## 4-2. 口座残高

**決定 5-2：残高は集計とは別の問いとして扱い、帳尻合わせを口座間の残高移動として数える。**

純残高（§3 決定 2）は「今月いくら増えたか」を、残高は「いま口座にいくらあるか」を答える。
帳尻合わせは純資産を動かさないので集計からは外す（決定 3）が、口座の中身は確実に動くので
残高では移動として数える。外すと、チャージした電子マネーの残高が永久に 0 のままになる。

```
残高 = 起点残高
     ＋ 収入の内訳
     − 支出・生活費・投資の内訳
     − 移動先を設定した帳尻合わせの内訳（出ていくぶん）
     ＋ 自分を移動先とする帳尻合わせの内訳（入ってくるぶん）
```

**決定 5-3：帳尻合わせの移動先（`Transaction.transferToId`）は任意にする。**
「銀行口座 → PayPay」のように移動先を選ぶと残高移動になる。
移動先が未設定の明細は、どちらの向きの移動か決まらないため残高に効かせない。
勝手に「移動元から出ていった」と決めると、あとで移動先を設定したときに二重に減る。
未設定の件数はダッシュボードと設定画面に出し、明細画面で設定できる。

**決定 5-4：残高を追うかは決済手段ごとに選ぶ（`PaymentMethod.trackBalance`）。**
クレジットカードは残高ではなく利用額なので、既定では追わない。
口座・現金・電子マネーは残高そのものなので既定で追う。

**決定 5-5：起点残高（`openingBalance`）と起点日（`openingBalanceAt`）を持つ。**
アプリを使い始めた時点の残高を入れる欄で、起点日より前の明細は
「起点残高に既に含まれている」とみなして数えない。
これが無いと、過去 1 年ぶんの CSV を入れた口座の残高が実際と合わなくなる。

## 4-4. 使途ごとの残高

**決定 32：口座残高とは別に、使途（個人・生活費・投資・彼女・家族 …）ごとの残高を持つ。使途は大項目の上に足す。**

口座残高は「いま口座にいくらあるか」、使途の残高は「そのお金は何（誰）のぶんか」を答える。
使途ごとに収入と支出を分けて持ち、その使途の残高の中でやりくりできているかを見たい。

```
使途 (Purpose, 追加自由)               ← 「使途」タブ。起点残高・起点日を持つ
   └ 大項目 (MajorCategory)           ← 大項目ごとに使途を 1 つ（「大項目」タブの「使途ID」列）
        └ 中項目 (Category)

使途の残高 = 起点残高
           ＋ その使途の収入（種別が個人収入の大項目の内訳）
           − その使途の支出（個人支出・生活費・投資の大項目の内訳）
           ＋ 振替で入ったぶん − 振替で出たぶん
```

- 大項目を使途に作り直すのではなく、使途を一番上に足した。今の大項目・中項目・明細をそのまま使え、
  イベント名（〇〇マラソン等）の段も残るため。種別は収入/支出の向きを決める役のまま残す
- 帳尻合わせ（チャージ・口座間の移動）は誰のお金も増減させないので、使途の残高には効かせない
- 使途を付けていない大項目（とアーカイブした使途の大項目）の内訳は「未設定」の行にまとめて出す
- 起点日より前の明細・振替は数えない（口座残高と同じ。決定 5-5）。今日より後の日付のものも残高には数えない
- 使途の残高の合計と口座残高の合計の差は「どの使途にも入っていないお金」として出す。
  起点残高の割り振り残しや、カードで使ってまだ引き落とされていないぶんがここに出る

**決定 33：使途の間でお金を回したときは「使途振替」として記録する。**
給料を「個人」で受けてから「投資」「彼女」へ回す、家族からの補助を「生活費」へ回す、のような動き。
口座のお金は動かないので明細ではなく別のタブ（「使途振替」: 日付・振替元・振替先・金額・メモ）に置く。
これが無いと、収入の無い使途（投資・彼女）の残高はマイナスが続くだけになる。

## 4-5. 二人（パートナーとの支出）

**決定 34：パートナーとの支出は、LINE ボット（別リポジトリ（非公開）の GAS）の「二人の明細」に一本化し、本体には自分用のページを足す。**

彼女との支出は LINE ボットが同じスプレッドシートの「二人の明細」「二人の精算」に記録し、本体の「明細」「内訳」へは
自分の負担（大項目「パートナー」の支出）と相手の分の立替（「立替 / 彼女立替」の帳尻合わせ・口座「彼女精算」への移動）として書く
（LINE ボット側の決定）。そのため本体の集計には、何もしなくても自分の負担だけが入る。
本体で内訳ごとに「誰の分か」を持つ方式（一度作ったもの）は、同じことを二重に持つことになるため取りやめた。

- 「二人」ページ: 未精算の差額と精算、月・期間の集計と 12 か月の推移、明細の絞り込み、精算の履歴（過去分の取込を区別）、
  イベント別（中項目、無ければメモ）、家計簿との突き合わせ（カード明細の取込待ち・書けなかった明細・消された明細、
  口座「彼女精算」の残高のずれ）
- タブ・見出しは GAS の gas/Config.js と一字一句同じにする。`db:seed` と起動時の自動補修は、無ければ GAS と同じ並びで作り、
  足りない見出しだけを右端に足す（GAS と同じ）。知らない列と「過去分の取込」タブには触らない
- 呼び名は「LINE連携」タブの表示名。自分は「自分」と出す。LINE のユーザー ID は画面に渡さない。実名をコード・テストに書かない

**決定 35：本体からも登録・修正・削除・精算できる。書き方は GAS とまったく同じにし、相手への LINE 通知は送らない。**

- 負担の割り方・割り勘の端数（払った側が持つ）・未精算の差額・本体の明細と内訳の書き方・カード払いの照合（同じカード・同じ金額・
  日付の差 3 日以内でちょうど 1 件）・精算額を直した差の扱いは、`src/lib/pair.ts`・`src/lib/pair-household.ts` に GAS から移した。
  同じ操作を GAS（テスト用ハーネス）とアプリで行い、本体の明細・内訳（重複判定キーまで）・二人の明細・二人の精算が一致することを確かめている
- 1 つの操作は 1 回の batchUpdate で書く（二人の明細と本体の明細が片方だけ書かれることが無い）。GAS のスクリプトロックには参加しないので、
  LINE とアプリでまったく同じ瞬間に書くと行番号がずれ得る（二人で使う規模では起きにくいとして受け入れる）
- LINE 通知はしない。通知するにはアプリが LINE のチャネルアクセストークン（秘密）を持ち、外部に接続する必要があるため（決定 15・16）
- 過去分の取込（種別 HISTORY）の精算は、取り込んだ明細ごと消し「過去分の取込」タブの結果も戻す必要があるため、アプリからは取り消さない
- 口座「彼女精算」の残高と比べる値 = 本体に書いた未精算の明細の差額 − 本体に書く前（取込待ち・エラー）に精算した明細の差額。
  精算は対象の差額を全部動かすので、取込待ちのまま精算すると、そのぶんだけ先に口座が動く（カード明細を照合すれば戻る）
- 本体の書き込み先（「立替 / 彼女立替」「彼女精算」）は GAS の `setup` が作る。無いときは明細だけを登録して家計簿反映を ERROR にし、
  「今すぐ照合」で書き直す（GAS の決定 L12 と同じ）

**決定 36：二人の明細と家計簿の明細を突き合わせ、同じ支払いを二重に持たないようにする。**

- 重なり: LINE で登録して本体にも書いた明細（家計簿反映 DONE）と、同じ決済手段・同じ金額・日付の差 3 日以内の取込明細（CSV・シート、内訳 1 件）。
  GAS はカード以外の決済手段を本体に書くので、PayPay・銀行を CSV でも取り込むと同じ支払いが 2 件になる。
  「取込明細にまとめる」で LINE の明細を消し、取込明細を自分の負担と立替に分けて LINKED にする（GAS のカード照合と同じ形）。外すと元に戻す
- カードの取込待ちは、自動の照合（ちょうど 1 件）で決まらないとき、同じ金額・14 日以内の内訳 1 件の明細から手で選べる
- 過去分の取込（HISTORY）は、家計簿に当時の明細が入っているので、どれに当たるかを覚えるだけ（「家計簿明細ID」に入れ、家計簿反映は NONE のまま）。
  家計簿の金額・内訳は変えない。GAS の照合でも使用済みとして扱われる。割り勘アプリの日付は旅行の日で、宿や飛行機は数か月前に払うことが多いため、
  同じ金額を 150 日前〜30 日後から探し、7 日以内にあればそれだけを候補にする。候補が 1 つ（かつ他の明細と取り合わない）ものはまとめて結び付けられる。
  相手が払った明細は、自分の家計簿に対応する明細が無いので照合しない

**決定 37：割り勘にしない「二人の時の出費」は、家計簿の明細に区分を付けてアプリの中だけで見る。**

- 「明細」タブに「二人の区分」列（SHARED = 割り勘（記録なし）/ SOLO = 自分だけ / SETTLEMENT = 精算の記録）を足す。空なら未確認。
  二人の明細に結び付いている明細は区分が空でも割り勘として扱う
- 対象は使途「彼女」の大項目（と大項目「パートナー」）の明細。金額はその明細のうち使途「彼女」の内訳の分（自分の支出として数えている額）
- LINE ボットは二人の明細だけを読むので、区分は相手のダッシュボードには出ない。GAS は知らない列を空のまま残す
- 区分は集計（収入・支出・使途）を変えない。見分けるためだけの印

**決定 38：彼女まわりは「中項目 ＝ イベント」に統一し、自分の出費のまとめを出す。**

- イベント別の集計は中項目で行う。二人の明細に中項目が無いときは、結び付けた家計簿の明細の中項目を使う
  （過去分の取込は家計簿側にしか中項目が無いことが多い）。大項目と同じ名前の中項目（パートナー / パートナー）はイベントとみなさない。
  どちらにも無い明細はメモごとに出し、中項目をまとめて付けられる（未精算は家計簿も書き直し、精算済みは家計簿の自分の負担の中項目も付け替える）
- 同じ中項目が並ぶ以前の大項目は「大項目をまとめる」でまとめる。まとめ元の中項目はまとめ先の同じ名前の中項目へ、
  まとめ元の大項目と同じ名前の中項目はまとめ先の大項目と同じ名前の中項目へ移し、無い名前はまとめ先に作る。
  内訳・予算（同じ中項目・同じ月は足し合わせる）・予定・分類ルール・二人の明細の中項目を付け替え、まとめ元はアーカイブする（消さない）。
  種別の違う大項目どうしはまとめない（金額の符号の意味が変わるため）
- 自分の出費のまとめ: 割り勘の自分の負担（二人の明細に結び付いた分 ＋ 割り勘（記録なし））＋ 自分だけ ＋ 精算の記録 ＋ 未確認
  ＝ 使途「彼女」の支出。家計簿の明細の日付で数え、月と全期間を並べる。参考に二人の明細の二人の総額・それぞれの負担（二人の明細の日付）
- 「二人」ページのタブは 5 つ: 概要 / 明細と精算 / イベント別 / 家計簿との照合（突き合わせ ＋ 過去分の照合）/ 二人の時の出費

## 4-3. 予実（予算・予定）

**決定 22：予算は中項目ごとに持ち、「毎月の既定」と「その月だけの上書き」の 2 段にする。**
`予算` タブの `月` が空の行が毎月の既定、`2026-12` のように月が入った行がその月だけの上書き。
上書きがあればそれを、無ければ既定を使う。ボーナス月や帰省の月だけ増やす、を行を増やさずに表せる。
アプリから「毎月」で保存したときは、表示中の月の上書きも一緒に外す（残っていると既定を変えても
その月の表示が変わらず、直したのに効かないように見えるため）。

**決定 23：予定は「毎月◯日に◯円」の定期の入出金として持ち、明細とは別のタブに置く。**
給料・家賃・通信費・積立など。`予定` タブに中項目・金額・日・口座（入金先/支払い元、帳尻合わせなら
移動先も）・開始月・終了月・有効を持つ。日が月末より大きい月は月末日にする（31 = 月末）。
予定から明細を自動で作ることはしない。実績は必ず取込か手入力で入れ、予定はそれと突き合わせるだけにする
（予定から作ると、取込んだ明細と二重になるため）。

**決定 24：予定と明細は、同じ中項目・同じ月の内訳のうち、金額がいちばん近いものと自動で突き合わせる。**
同じくらいなら日付が近いものを選ぶ。1 つの内訳は 1 つの予定にしか使わず、金額の大きい予定から順に取る。
これで「通信費」に docomo と Netflix の 2 つの予定があっても、それぞれに対応づけられる。
突き合わせた結果は保存せず、表示のたびに計算する（明細を直せば結果も追従する）。
状態は「済（明細あり）」「まだ（予定日前）」「期日超過（予定日を過ぎても明細なし）」の 3 つ。

**決定 25：予（比べる相手）は予算、無ければ予定の合計にする。二重には数えない。**
家賃のように予定だけ登録した中項目も、予算を別に入れなくても予実に出る。
同じ中項目に予算と予定の両方があるときは、予算を上限とみなし、予定はその内訳として扱う。

**決定 26：月末の見込みは楽観的にならない側に倒す。**

```
支出・生活費・投資 = 実績 ＋ まだ来ていない予定 ＋ 予算の残り（予定ぶんを除き、使い切る前提）
収入               = 実績 ＋ まだ来ていない予定（収入の予算は目標であって確約ではないので足さない）
口座残高           = 今の残高 ± その月末までに来る、まだ来ていない予定（口座を指定したもの）
```

予算はどの口座から出るか決まらないので、口座残高の見込みには入れない。
先の月を開くと、今月からその月までの予定を積み上げた残高を出す。過ぎた月は見込みを出さない。

**決定 27：「今日」「今月」は日本時間で決める。**
Codespace のサーバーは UTC で動くため、そのままだと毎月 1 日の 0〜9 時が前の月扱いになり、
予定の「期日超過」の判定も 1 日ずれる。ダッシュボード・まとめ・予実・手入力の日付の既定値で共通にする。

### 4-1. 入金を収入にするか、差し引くか

**決定 16：入金（お金が入ってくる行）の扱いは決済手段の種類で決める。取込では行ごとに切り替えられる。**

集計は口座ベースで行うので、外から入ってきたお金は収入にする。一方、自分の財布の中での移動や
買い物の取り消しは収入ではないので、その中項目から差し引く。

| 決済手段 | 入金の扱い | 例 |
|---|---|---|
| 銀行・現金 | 収入 | 給料振込、人から受け取った現金、交通費の精算 |
| 電子マネー | 人から受け取ったもの（内容に「受取 / 受け取」）は収入、それ以外は差し引き | PayPay の受け取り / チャージ・ポイント |
| クレジットカード | 差し引き | 返品・取消 |

収入にする入金の行き先:

1. 使用先と**同じ名前の個人収入の中項目**（例: 使用先「2024夏インターン費用」→ 交通費支給（インターン）/ 2024夏インターン費用）
2. 無ければ、同じ名前の投資・帳尻合わせの中項目（資産の移動）
3. 使用先が大項目の名前と同じなら、その大項目の同名の中項目（使用先「給料」→ 給料 / 給料）
4. どれも無ければ、受け皿の大項目「収入内訳」の下に同じ名前で作る

出金や差し引きの入金は、同じ名前でも個人収入以外の中項目に入る。
規則は `src/lib/inflow.ts`（種類の判定）と `src/lib/import-routing.ts`・`src/lib/sheet-source.ts`（行き先）にある。

## 5. 取引データの入力

### 5-1. CSV インポート

**決定 6：カード会社ごとの専用パーサは作らず、汎用マッピング UI ＋ プリセット保存で対応する。**

取り込みは 3 ステップ:

1. **ファイルを選ぶ** — 文字コード（自動判定 / Shift_JIS / UTF-8）、先頭の読み飛ばし行数を指定
2. **列を対応づける** — 日付・利用先・金額（必須）、入金列・メモ・決済手段（任意）。
   ヘッダー名から初期値を自動推測する。この設定は「楽天カード」などの名前でプリセット保存でき、
   次回は選ぶだけで済む
3. **分類を確認して取り込む** — ルールで自動分類した結果を 1 行ずつ確認・修正して確定

対応済みの実データ差異:

| 差異 | 対応 |
|---|---|
| Shift_JIS のカード明細 | バイト列から自動判定してデコード（`encoding-japanese`） |
| ヘッダーの前に説明行がある銀行明細 | 「先頭の読み飛ばし行数」で対応 |
| 出金列と入金列が分かれている | 「入金列」を指定すると、その行は収入として扱う |
| 負の数が支出の明細 | 「金額の符号」を `負の数が支出` に切り替える |
| `¥1,234` `△1,234` `(1,234)` `1234円` | いずれも数値として解釈する |
| `2026/8/3` `2026-08-03` `2026年8月3日` `20260803` | いずれも日付として解釈する |
| 全角の利用先（`ＰａｙＰａｙ`） | NFKC 正規化して半角と同一視する |
| `使用先` でイベント別に持つ明細 | 使用先列を中項目にする。無い中項目は取込時に作る |
| `個人支出` と `生活費` が別列 | 2 つの内訳に分けて登録する（§2） |

**決定 7：重複判定は「日付 + 利用先 + 金額 + 決済手段」の 4 点のハッシュで行う。**
利用先は NFKC 正規化・空白除去・小文字化してから比較するため、表記ゆれでは別明細にならない。
同じ日に同じ店で同じ額を 2 回使った場合は正当な 2 件なので、
「重複チェックに引っかかる行も取り込む」を選べば連番を振って両方登録できる。

**決定 8：取り込みはバッチ単位で丸ごと取り消せる。**
列マッピングを間違えたときに 1 件ずつ消す作業を避けるため。

### 5-2. 手入力

支出・収入・チャージを 1 件登録するフォーム。選んだ中項目の大項目で扱いが決まるため、
収入用・支出用にフォームを分けていない。

## 6. 自動分類ルール

**決定 9：GAS のキーワード判定を、編集可能な「ルール」テーブルとして持つ（ハードコードしない）。**

- 判定方式: 含む / で始まる / 完全一致 / 正規表現
- 優先度（0〜999、小さいほど先に判定）→ 判定方式の限定度 → キーワードの長さ、の順に評価し、
  最初に当たったルールを採用する
- 初期投入（`src/lib/db/seed-data.ts`、約 250 件）は、よくある店名・事業者の実際の表記（全角・半角カナ・略称）から起こした
  - 中項目まで決めるのは、使用先がいつも同じだった引き落とし・店だけ
    （電気・ガス・水道→光熱費、Spotify/Netflix→サブスク、給料振込→給料、PayPay のポイント→ポイ活、
    交通系 IC のチャージ→チャージ関連 など）
  - それ以外は費目だけ（スーパー・コンビニ・チェーン店→食費、鉄道・飛行機・ETC・カーシェア・IC カードの乗車記録→交通費、
    宿泊予約サイト→宿泊費、衣料品店→衣服、ドラッグストア・100 円ショップ→日用品、大会のエントリー→趣味）。
    旅行先の店のように使用先がイベントごとに変わるものは、使用先で中項目を決める
  - 人とのやりとり（送金・受け取り）は相手の名前になるので入れない
  - `db:seed` は同じキーワード・判定方式のルールが無いときだけ足す（自分で直したルールは変えない）
- 照合では、利用先とキーワードの両方の表記ゆれを吸収する。正規化（NFKC・空白除去・小文字化）に加えて、
  長音とハイフン・ダッシュ（ー・－・―・-・ｰ）を同じものとみなし、小さい仮名を大きい仮名とみなす
  （カード明細の「セブン－イレブン」「フアミリ―マ―ト」「ブツキング・ドツトコム」を、キーワード「セブン-イレブン」
  「ファミリーマート」「ブッキング」で拾うため）。重複判定キーにはこの吸収を使わない（既存の明細の判定を変えないため）
- コンビニ・スーパーは優先度 60 で、駅名（「ＪＲ」「地下鉄」…）より先に効かせる（「セブン-イレブン - 福岡市地下鉄姪浜駅」が食費になるように）。
  宿泊は優先度 55 で「スーパー」より先に効かせる（「スーパーホテル」が宿泊費になるように）。
  百貨店と同じ名前の鉄道会社（阪急・東急…）は、電鉄・鉄道・電車が付いたときだけ交通費にする

**決定 10：学習は「完全一致ルールの自動生成」で実装する。**
明細画面でカテゴリを直すと、その利用先の完全一致ルール（優先度 50、`学習` バッジ付き）が作られ、
次回以降の同じ利用先が自動で同じカテゴリになる。

完全一致にしたのは誤爆を避けるため。`AMAZON.CO.JP 12345` のように毎回変わる利用先は
完全一致では再ヒットしないので、その場合は設定画面で「含む」に変え、キーワードを短く直す。

### グラフの決定事項

**決定 12：月別推移は「収入の棒 ＋ 支出/生活費/投資の積み上げ棒 ＋ 純残高の折れ線」にする。**
4 系列を横並びにすると 12 か月 × 4 本で細くなりすぎる。
出ていくお金は積み上げると合計として意味を持つが、収入を同じ積み上げに入れると意味を成さないため分けた。

**決定 12（改訂）：ダッシュボードの月別推移は、使途ごとのスモールマルチプルにする。**
使途ごとに 1 枚、月ごとに「入ったお金（収入＋振替で入ったぶん）」と「出たお金（支出＋振替で出たぶん）」の棒を並べる。
見たいのは同じ使途の中の入と出の釣り合いなので、縦軸は使途ごとに取る（個人と彼女では桁が違う）。
シート画面の推移は、請求シートに使途が無いため従来の形（収入の棒 ＋ 出ていくお金の積み上げ ＋ 純残高）のまま。

**決定 13（再改訂）：ダッシュボードの円グラフは二重円にする。内側 = 入ってきたお金、外側 = 使ったお金（中項目ごと）。**
表示するのは割合ではなく金額。2 つの輪の合計をそろえるため、使ったお金が多い月は内側に「貯金から」、
残った月は外側に「貯金へ」を足す。穴の中にその差（残った / 足りない）を出す。
使途を選ぶとその使途だけになり、振替はその使途の入金（◯◯から振替）・出金（◯◯へ振替）として並ぶ。

- 色は内側が green、外側が blue の 1 色の濃淡（大きいほど濃い）。区分が少ないときは薄い側の段から使う
- 輪ごとに 6 区分まで。6 つ目以降は「その他」（濃い灰色）にまとめ、一覧には全項目を出す
- 「貯金から / 貯金へ」はほぼ白の灰色。どちらの輪の隣り合う段とも見分けられることを検証済み
- 狭い画面では扇の外のラベルを出さない（切れるため）。金額は下の一覧と吹き出しで読める

**決定 13（改訂）：中項目の内訳は横棒、大項目ごとの支出は金額表示の円グラフにする。**（ダッシュボードは上の二重円に置き換え。シート画面は引き続きこの円グラフ）
中項目は 10 件以上になり、円グラフでは角度が読めないので横棒のまま。
当初は種別（支出・生活費・投資）の構成をドーナツで出していたが、種別の内訳は数字で足りるので外し、
代わりに**大項目（インターン・旅行・日常 …）ごとの支出**を円グラフにした。表示するのは割合ではなく金額。

- 円は 6 区分まで。上位 5 つを超える大項目は「その他」にまとめる。一覧には全大項目の金額を出す
- 色は 1 色の濃淡（大きいほど濃い）。どの大項目かは扇形の横の名前と一覧で示す。
  大項目ごとに色を固定する方式は、4 色を超えると月によって見分けにくい色が隣り合い得るため採らなかった
- 払い戻しで差し引きマイナスになった大項目は円に描けないので、一覧の下に分けて出す

**決定 14：系列色はライト/ダークで別々に選び、色覚特性の検証を通したものだけを使う。**（決定 30 で、デジタル庁デザインシステムの色から選び直し、ライトのみにした）
隣接する系列の色差（CVD シミュレーション込み）と背景コントラストを検証済み。
帳尻合わせは集計に効かない系列なので、グラフの系列としては使わず意図的に無彩色にしている。
金額の文字は系列色ではなくインク色にし、色の横のドットだけが identity を担う
（色だけで意味を伝えないため）。

## 10. データの置き場（Google スプレッドシート）

当初は PostgreSQL（Vercel + マネージド Postgres、のちに Codespace 内の Docker）で動かしていたが、
次の理由でデータの置き場を Google スプレッドシートに移した。

- Codespace 内の Docker に DB を置くと、Codespace を作り直した時点でデータが消える
- 版履歴（誤操作の取り消し）を自前で用意する必要がある
- GAS 時代と同じく、スプレッドシートで直接見て直せることに価値がある

**決定 15：アプリはインターネットに公開しない。**
外部から到達できる URL を持たせない。PC か Codespace の中で動かし、待ち受けは `127.0.0.1` に限る。
使うたびに起動する手間は受け入れる。

**決定 16：スプレッドシートへはサービスアカウントで接続する。**
サービスアカウントは共有されたファイルにしか触れないので、鍵が漏れても被害はこのスプレッドシートに
限られる。鍵は Codespaces のシークレットで渡すのを推奨し、ファイルで置く場合も `secrets/` を
`.gitignore` する。

**決定 17：タブと見出しは日本語にし、列は見出しの名前で探す。**
スプレッドシートを人が読めることが目的なので、タブは `明細`・`内訳`・`大項目` のように、
見出しも `日付`・`利用先`・`金額` のようにする。列の位置には依存しないので、並べ替えや
自分用の列の追加は自由。見出しの文字を変えるとその列は見えなくなる（`db:seed` で補える）。

**決定 18：1 画面の表示で読むのは 1 回、1 回の保存で書くのも 1 回。**
全タブを 1 回の `values:batchGet` で読み、メモリ上で集計する。書き込みは変更を積んで
1 回の `batchUpdate` にまとめる。`batchUpdate` は 1 つでも失敗すると何も適用しないので、
明細だけ書かれて内訳が無い、という中途半端な状態は起きない。Sheets API の回数制限
（1 分あたり 60 回）にもかかりにくい。

**決定 19：外部キー・一意制約の代わりに、アプリ側で検証し、壊れていれば知らせる。**
スプレッドシートは手で行を消せるため、Postgres が保証していた「内訳は存在する中項目を指す」
といった関係は保証されない。

- 同名の大項目・中項目、同じキーワードのルール、重複した明細は、保存前にアプリが弾く
- 参照先が見つからない内訳は「不明な中項目」として表示し、集計からは外す（画面は落とさない）
- `npm run sheets:check` がこうした食い違いを一覧する。勝手には直さない
  （どう直すのが正しいかは、消した理由によって変わるため）

**決定 20：書き込みは必ずスプレッドシートを読み直してから行う。**
更新・削除は行番号を指定するため、キャッシュした古い行番号を使うと別の行を書き換えかねない。
画面表示の読み込みは手元の写しを使い回す（決定 29）が、書き込みの前は必ず読み直す。

**決定 21：セルへは値の種類を明示して書く。**
文字列は `stringValue`、数値は `numberValue` として書く。CSV から来た利用先が
`=IMPORTXML(...)` のような式の形をしていても、式として実行されずに文字列のまま保存される。

**決定 28：GAS 時代の請求シートは、アプリのデータとは別のファイルとして、同じサービスアカウントで読むだけにする。**
「シート」画面（[`spreadsheet-source.md`](spreadsheet-source.md)）は、請求シートを読み取り専用で集計し、
アプリのデータと突き合わせる。請求シートはサービスアカウントに「閲覧者」で共有し、アプリは
`spreadsheets.readonly` のスコープでトークンを取って読む。共有の権限とスコープの両方で、
アプリから請求シートを書き換えることはできない。鍵を 2 つに分けないのは、管理する秘密を増やさないため。
以前の設定（`GOOGLE_SERVICE_ACCOUNT_EMAIL` ＋ `GOOGLE_PRIVATE_KEY`）も鍵の渡し方として読める。

**決定 29：起動時に全データを読み込み、画面は手元の写しから描く。**
スプレッドシートが正であることは変えない。そのうえで、サーバーの起動時（`src/instrumentation.ts`）に全タブを読み込み、
画面は待たずに表示する。写しは 30 秒間そのまま使い、それを過ぎたら手元の写しで表示しつつ裏で読み直す
（10 分より古ければ読み直し終わるまで待つ）。アプリからの書き込みは直前に読み直し、直後の表示でも読み直すので、
保存した内容が古い写しに隠れることはない。スプレッドシートを直接直した内容は 30 秒以内に反映され、
画面右上のボタンで即座に読み直すこともできる。
Sheets API は通常の利用は無料で、制限（読み取り 1 分 60 回／ユーザー）を超えた分だけが 2026 年中に課金対象となる予定のため、
この方式で読み取りを 30 秒に多くて 1 回に抑え、プロジェクトに請求先アカウントを紐づけない運用にする。

**決定 30：見た目はデジタル庁デザインシステムに合わせる。**
デザイントークンは公式の `@digital-go-jp/tailwind-theme-plugin` を使い、部品の作りは公式のコードスニペット（React 版）に倣う。
フォーカスの黒枠＋黄色リング、最小 14px・本文 16px の文字、Noto Sans JP、キーカラー（key-900）の主ボタンと現在地表示をそろえる。
種別の色はデザインシステムの色から選び直し、dataviz の検証（色覚特性シミュレーションを含む）を通したものを使う。
デザインシステムに暗い配色の定義が無いので、ダークモードはやめた（決定 14 の暗い配色は廃止）。

**決定 31：請求シートの過去の明細は、「シート」画面から取り込めるようにする。読み方は集計と同じにする。**
取り込む前に、書き込まずに見込み（件数・新しく作る中項目と決済手段・月別の件数）を出す。
請求シートはサーバーで読み直し、画面から送られた行は使わない。
取り込みは 1 回の書き込みにまとめるので、途中で失敗しても一部だけ入ることはない。取込履歴に残るので、まとめて取り消せる。
- 使用先の無い行は取り込まない（GAS のまとめと同じく、カードの引き落としとの二重計上を防ぐ）
- 重複は既存の判定キー（日付・利用先・金額・決済手段＋連番）で見る。シートの中で k 回目に出てきた同じ内容の行は、連番 k のキーで判定する。
  何度取り込んでも増えず、同じ日に同じ運賃を 2 回払ったような正当な重複も落とさない
- 使用先に当たる中項目が無ければその名前で作る（作る先の大項目は選べる）。作らない場合は自動分類ルール → 未分類
- ブロック名に当たる決済手段が無ければ作る（種別は名前から推測し、設定で直せる）
- 取り込んだ明細の入力経路は `SHEET`。取り込んだあとは、「シート」画面の突合が一致する
