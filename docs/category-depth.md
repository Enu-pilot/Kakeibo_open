# 項目の細分化をどう持つかの検討

「中項目をさらに細かく分けたい」への設計メモ。

> **案 B を採用して実装した**（要件定義 §3-2 決定 15）。費目の初期データは
> 食費 / 食費（遊び）/ 交通費 / 宿泊費 / 衣服 / 日用品 / 趣味。クロス集計は「まとめ」と「シート」画面にある。
現在の階層は [`requirements.md`](requirements.md) §3 のとおり
**種別 → 大項目 → 中項目** の 3 段で、これ以上下の段は無い。

---

## 1. 実際に持っている構造

まとめシートの項目名から起こすと、いまの運用はこうなっている。

| 段 | 中身 | 例 |
|---|---|---|
| 種別 | 固定 5 種 | 収入 / 支出 / 生活費 / 投資 / 帳尻合わせ |
| 大項目 | 生活の領域 | インターン / バイト / 旅行 / 日常 / 遊び / パートナー |
| 中項目 | **イベント名** | 夏の旅行 / 冬の旅行 / 夏のインターン / 〇〇マラソン |

（数は運用で増減する。）中項目が食費・交通費のような**費目ではなくイベント**なのが特徴で、
これは GAS の `使用先` 列をそのまま中項目にしてきた結果でもある。

そのうえで「夏の旅行の中を交通費・宿泊・食事に分けたい」というのが今回の要望になる。

---

## 2. これは「4 段目」ではなく「2 本目の軸」

ここが判断の分かれ目になる。欲しいのは

```
旅行 ─ 夏の旅行 ─ 交通費
               ├ 宿泊
               └ 食事
```

という木に見えるが、同じ `交通費` は 冬の旅行 にも 一人旅 にも出てくる。
木として持つと**費目がイベントの数だけ複製される**。旅行のイベント 10 件 × 費目 5 種で 50 件、
しかもイベントが増えるたびに費目一式を作り直すことになる。

実態は木ではなく、**イベント軸 × 費目軸のクロス**である。

```
              交通費   宿泊   食事
  夏の旅行      ●      ●     ●
  冬の旅行      ●      ●     ●
  一人旅        ●      ●     ●
```

この見立てが、以下の案の優劣をほぼ決める。

---

## 3. 案の比較

| | 案A 4 段目を足す | 案B 費目の軸を足す | 案C 中項目名で表す |
|---|---|---|---|
| 変更の大きさ | 大 | 中 | **なし** |
| 費目の重複 | イベントごとに複製 | **1 セットを共有** | イベントごとに複製 |
| イベント合計 | 出る | 出る | 出る |
| 費目合計（全イベント横断） | 出る | **出る** | 出ない |
| まとめ表 | 縦軸が 4 段になり作り直し | 今のまま＋クロス集計を追加 | 今のまま |
| 取込 | 4 段目を決める手段が無い | 内容から分類ルールで当てられる | 手で名前を付ける |

### 案C（中項目名で表す）

`夏の旅行・交通費` `夏の旅行・宿泊` のように名前で表す。変更ゼロで今日からできる。
ただし中項目が掛け算で増え、**「旅行全体の交通費はいくらか」が出せない**
（名前の前方一致に頼ることになる）。一時しのぎとしては成立する。

### 案A（中項目の下にもう 1 段）

`Category` に親子を持たせるか、`SubCategory` を足す。素直だが、
§2 のとおり費目が複製される。加えて、まとめ表の縦軸・CSV 書き出し・絞り込み・
グラフの内訳がすべて 4 段前提に変わる。取込の「使用先を中項目にする」も、
4 段目まで自動では決められない。

### 案B（費目の軸を足す）← 推奨

中項目（イベント）はそのままに、**内訳に「費目」を 1 つ持たせる**。

スプレッドシートでは「費目」タブ（ID・名前・並び順・アーカイブ日時・作成日時）を足し、
「内訳」タブに「費目ID」列（空でもよい）を足す。

```
費目     ID | 名前 | 並び順 | アーカイブ日時 | 作成日時
内訳     … | 費目ID   ← 空なら「未設定」
```

内訳に「費目ID」列を足すだけで、既存の列は変えない。
**空でよい列の追加なのでデータ移行は不要**、既存の集計も無変更で通る。

なぜ内訳（split）に持たせるか: 1 回の買い物が交通費と宿泊にまたがる場合は、
**既にある内訳の仕組みで 2 つに割れる**（要件定義 §2）。
新しい仕組みを足さずに済む。

なぜ複数タグにしないか: 1 つの内訳に費目を複数付けられるようにすると、
費目別に合計したときに同じ金額が二重に数えられる。
**単一参照にして、分けたいときは内訳を割る**のが、いまの金額の持ち方（§4 決定 5）と整合する。

## 4. 案Bを採る場合に足りるもの

| 箇所 | 追加 |
|---|---|
| スキーマ | 「費目」タブ 1 つ ＋ 内訳の「費目ID」列（空可） |
| 設定画面 | 費目の追加・改名・並べ替え（カテゴリと同じ作り） |
| 明細 | 費目の列と絞り込み |
| 取込 | プレビューで費目を当てる。利用先からの推測は**既存の分類ルールの仕組みがそのまま使える** |
| 集計 | 「イベント × 費目」のクロス集計を 1 本追加。既存のまとめ表は変えない |

自動分類との相性がいいのも案 B の利点になる。
中項目（イベント）は店名からは推測できない（どの旅行かは店名に出ない）が、
**費目は店名から推測できる**（セブンイレブン → 食費）。
いまのルール機構は「利用先 → 中項目」だが、これを「利用先 → 費目」に向けると素直に効く。

なお要件定義 §1 で取り込まないことにした GAS の `食費判定` 列は、
この費目軸ができれば収まり先ができる。必要になったら取り込みを足せばよい。

## 5. 未決事項

1. **費目の粒度。** 食費・交通費・宿泊・入場料…をどこまで分けるか。
   案 B なら後から増やせるので、最初は粗くてよい。
2. **既存の中項目の扱い。** 費目は null のままでも集計は通る。
   遡って付けるかどうかは運用次第。
3. **どちらの軸を階層にするか。** いまは中項目＝イベント。
   逆（中項目＝費目、軸＝イベント）にもできるが、`使用先` 列がイベントである以上、
   取込の流れは今のままのほうが素直。
4. **案 C を先に当てるか。** 数件だけ細分化したいなら名前で足りる。
   横断で費目を見たくなった時点が案 B の入れどき。
